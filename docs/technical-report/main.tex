\begin{abstract}
Large-language-model (LLM) agents are increasingly used to run laboratory instruments.
We report the Quantum Sensing Agent (\qsa{}), an LLM agent that operated a room-temperature scanning-confocal setup for nitrogen-vacancy (NV) centers in diamond starting in February 2025; to our knowledge, this makes it among the earliest LLM agents to operate a quantum-sensing experiment.
\qsa{} chains confocal scans, zoomed emitter searches, focusing, and continuous-wave optically detected magnetic resonance (ODMR).
It changes only parameter values in JSON configurations, runs four allow-listed measurement scripts, and reads the resulting plots with a vision model, under the supervision of an experimenter.
Later versions added explicit assistant and auto modes and retrieval over past sessions and their plots, intended to let the agent learn from earlier attempts.
Over 16 hardware sessions on 10 days (18 February -- 16 June 2025) the agent completed 73 measurements.
In the best session it worked through six operator-selected candidates over 3.4 hours, proposed causes when two showed no resonance, and recorded an ODMR spectrum with two dips near 2.863 and 2.878\,GHz on the third; across the deployment it turned all 22 numerical instructions from the operator into exactly the requested configurations.
We also document its failures: low ODMR contrast, unreliable reading of coordinates from images, no observed benefit from retrieval on the hardware, and LLM replies that invented tool output, which in a short unsupervised test led the agent to report fabricated results as its own progress.
We distill these observations into lessons for building agents for quantum laboratories.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Running a quantum-sensing experiment involves a long chain of routine but judgment-laden steps: map a sample, pick a candidate emitter, centre on it, focus, choose a microwave window and power, decide whether a flat spectrum means a bad emitter or a bad setup, and move on.
Classical automation optimizes \emph{within} one of these steps, for example by choosing ODMR frequencies adaptively~\cite{dushenko2020odmr} or focusing on point emitters~\cite{sahoo2023find}.
Deciding \emph{which} step to run next, and interpreting a failure in words, has remained the experimenter's job.
LLM agents that call tools are a natural candidate for this role.
They had already planned and executed chemistry experiments~\cite{boiko2023coscientist,bran2023chemcrow}, operated scanning-probe microscopes~\cite{liu2024microscopy,mandal2024aila}, and calibrated a superconducting quantum processor~\cite{cao2024kagents}.

This report documents \qsa{}, an LLM agent (Claude, via the Anthropic API) that operated a scanning-confocal NV-center ODMR setup in the Yacoby lab at Harvard.
\qsa{} ran its first hardware session on \textbf{18 February 2025}, its main deployment ended on 14 May 2025, and a last, short auto-mode test ran on 16 June 2025.
We describe the system as built and the deployment as logged.

To our knowledge, \qsa{} is among the earliest demonstrations of a large-language-model agent operating a quantum-sensing experiment.
Its first session on an NV-center confocal setup took place on 18 February 2025; this date rests on the timestamps inside the session log \code{agent\_history.log}, which entered the repository in its first commit on 3 April 2025 (\code{17c17e1}).
The earliest NV-center LLM-agent study we found was posted in July 2026~\cite{isogawa2026nv}.
The earliest LLM-agent quantum-sensor study on any platform we found was posted in August 2025~\cite{sha2025qcopilot}.
Comparable later systems go further than \qsa{}.
Isogawa et al.~\cite{isogawa2026nv} run pulsed Ramsey and CPMG measurements autonomously over many hours.
\qsa{} ran CW ODMR with a human at the setup directing each step; per-action approval was enforced in the February--April versions.
We also note that this comparison is asymmetric: our date comes from internal logs, while other groups' dates are arXiv posting dates, and their experiments may have run earlier.

\paragraph{Contributions.}
\begin{enumerate}[leftmargin=*]
  \item \textbf{A closed-loop agent on a real NV confocal-ODMR setup.} \qsa{} chains a galvo scan, a zoomed emitter search, a z-focus optimization and a CW-ODMR sweep, writing each configuration and reading each plot itself, with the operator choosing candidates and frequency windows (Sections~\ref{sec:system} and~\ref{sec:case}).
  \item \textbf{A conservative tool design.} The agent can only edit parameter values in JSON configurations, run four allow-listed scripts in a fixed command format, and read or write inside two folders. In the February--April versions every write, run and vision action needed the operator's approval (Section~\ref{sec:safety}).
  \item \textbf{Memory of past sessions and their plots.} Sessions are embedded on exit together with the names of the plots they refer to, so a later session can retrieve earlier attempts and reopen the old figures with vision (Section~\ref{sec:memory}). We present this as a design feature: it was built and tested in software, and no hardware log shows it changing behaviour.
  \item \textbf{A deployment record with lessons learned.} 73 completed measurements in 16 hardware sessions on 10 days (18 February -- 16 June 2025), with a 14 May case study, statistics on guidance, permissions and failures, and an analysis of what went wrong, including an unsupervised run that believed its own invented results (Section~\ref{sec:results}).
\end{enumerate}

\section{Related work}
\label{sec:related}

\paragraph{LLM agents operating laboratory instruments.}
Coscientist~\cite{boiko2023coscientist} and ChemCrow~\cite{bran2023chemcrow} established the ``LLM plus tools plus instrument API'' pattern in chemistry; self-driving laboratories more broadly are reviewed in~\cite{tom2024sdl}.
In microscopy, Liu et al.~\cite{liu2024microscopy} used GPT-4 with instrument APIs for scanning-probe workflows, and AILA~\cite{mandal2024aila} ran atomic force microscopy with a multi-agent LLM and found frontier models fragile and prone to deviating from instructions.
That finding motivates \qsa{}'s restrictive tool layer.
Later agents at beamlines, accelerators and cryogenic transport setups are listed in Appendix~\ref{app:related}.

\paragraph{LLM agents for quantum hardware.}
k-agents~\cite{cao2024kagents}, posted in December 2024, calibrated a superconducting processor before \qsa{}; it is the reason we do not claim to be the first LLM agent on quantum hardware.
Later work on other quantum platforms is summarised in Appendix~\ref{app:related}.
For quantum sensing specifically we found two studies.
QCopilot~\cite{sha2025qcopilot} optimizes laser cooling for a cold-atom sensor and keeps a knowledge base of past experiments.
Isogawa et al.~\cite{isogawa2026nv} operate a confocal NV setup with persistent project records and run Ramsey and CPMG sequences; theirs is the closest work to ours.
Classical automation of NV experiments, such as adaptive Bayesian ODMR~\cite{dushenko2020odmr}, optimizes inside a fixed protocol (Appendix~\ref{app:related}); \qsa{} instead decides which protocol to run next, and the two are complementary.

\paragraph{Agent memory.}
Retrieval-augmented generation~\cite{lewis2020rag} and episodic or reflective memories~\cite{shinn2023reflexion,park2023generative,wang2023voyager,zhao2023expel} let agents reuse past experience; simple trajectory retrieval is a strong foundation for agent memory, especially when combined with fine-tuning~\cite{ferraz2026exprag}.
QCopilot, Vriza et al.\ and Isogawa et al.\ keep lab memories, and all three appeared after \qsa{}'s February 2025 deployment.
\qsa{} additionally stores, with each retrieved chunk, the names of the plots it refers to, so that the agent can reopen those figures.

\section{System}
\label{sec:system}

\subsection{Apparatus and physics}
\label{sec:apparatus}

The negatively charged NV center has a spin-1 ground state whose $m_s=\pm1$ levels lie $D\approx2.87$\,GHz above $m_s=0$ at room temperature.
A field component $B_\parallel$ along the NV axis splits the $\pm1$ levels by $2\gamma B_\parallel$, with $\gamma\approx2.8$\,MHz/G.
Green excitation pumps the spin into $m_s=0$, and the $\pm1$ states fluoresce less.
A resonant microwave field therefore produces a dip in the count rate, and sweeping the frequency gives the ODMR spectrum~\cite{doherty2013nv}.
All spin measurements in this project are such CW sweeps; the repository contains no pulsed sequences.

The setup is a room-temperature scanning-confocal microscope controlled by the lab's Python stack (\code{pylabcontrol} with \code{b26\_toolkit}) on a Windows PC.
The agent drives four thin command-line wrappers, each of which loads a JSON configuration, runs the corresponding toolkit class, and saves a PNG plot and a JSON data file: \code{galvo\_scan} (a raster of the field of view), \code{find\_nv} (a zoomed scan with a 2D Gaussian fit around a chosen point), \code{optimize} (z-focus) and \code{ESR} (a CW microwave sweep); hardware and defaults are in Appendix~\ref{app:apparatus}.
The intended workflow, which the system prompt states, is galvo scan $\to$ choose a spot $\to$ \code{find\_nv} $\to$ \code{optimize} $\to$ ESR, repeated for each NV.

\subsection{Agent loop and tools}
\label{sec:loop}


Figure~\ref{fig:workflow} (Appendix) shows the loop.
The prompt consists of a system instruction (abridged in Appendix~\ref{app:prompt}) followed by the session transcript.
The model must answer with one \code{<think>} block, containing its reasoning, and \code{<action>} blocks of JSON whose \code{type} is \code{message} (talk to the operator), \code{read} or \code{write} (read a configuration, or write a modified one into the run's \code{configs/} folder), \code{run} (launch one of the four scripts), \code{vision} (send a saved plot to the vision model) or, from June 2025, \code{rag\_search} (retrieve past sessions).
Script standard output and vision results are appended to the transcript, so the next LLM call sees them.
Every session gets a run folder with \code{configs/}, \code{data/} and \code{logs/}.
The log records each operator message, raw LLM reply, extracted reasoning, action, permission decision and script output with a timestamp, so every measurement can be traced to the configuration that produced it.
The deployment analysis in Section~\ref{sec:results} rests entirely on these logs.

\paragraph{Models.} Every version calls Claude through the Anthropic API: Claude 3.5 Sonnet in February 2025, and Claude 3.7 Sonnet, including image analysis, from March 2025 onward (authors' record). The logs do not record the model. The committed code (April 2025 on) defaults to Claude 3.5 Sonnet for text and Claude 3.7 Sonnet for vision, so the text model of a later session depended on a local setting that we cannot check; we keep the authors' record as the default.

\paragraph{Prompting and vision.} The system instruction (Appendix~\ref{app:prompt}) tells the agent to read the default configuration first and change parameter values only. Until June the history was serialized into a single flat \code{User:}/\code{Assistant:} transcript; Section~\ref{sec:failures} shows why this mattered. Plots of every type are read through the \code{vision} action.

\subsection{Safety and permission model}
\label{sec:safety}

The agent never touches instrument drivers directly. Four restrictions define what it can do:
\begin{enumerate}[leftmargin=*]
  \item \textbf{Configuration-only edits.} The agent changes measurement settings only by writing JSON files. The prompt requires it to keep the exact keys, structure and types of the default configuration.
  \item \textbf{Allow-listed scripts.} A \code{run} command is parsed against a fixed pattern, \code{py <name>.py --config <file> --output-dir <dir>}, and the script is checked against an allow-list of the four wrappers; anything else is rejected with an error message that is fed back to the agent.
  \item \textbf{Folder whitelist.} Reads and writes are restricted to the \code{configs} and \code{data} folders.
  \item \textbf{Permission gate.} In the February--April versions, every write, run and vision action waited for an explicit ``yes'' from the operator at the console, and refusals were fed back to the agent. In the logs, the whitelist and allow-list rejected 9 reads, 3 writes and 4 run commands, all in short development sessions.
\end{enumerate}
The version used on 14 May logged no permission prompts.
There, write and run actions executed in the same turn in which the agent asked ``May I proceed?''.
Control was turn by turn instead: every LLM call followed an operator message.
The June 2025 code makes the gate explicit as an \emph{assistant} mode and adds an \emph{auto} mode that grants permissions, logs them, and stops after at most 10 consecutive steps.
June versions also execute only the first action in each reply.
The only hardware session with the June code, on 16 June 2025, ran in auto mode (Section~\ref{sec:june}).

\subsection{Memory and retrieval over past sessions}
\label{sec:memory}

The motivation for memory is that a lab agent should learn from earlier attempts: which windows showed resonances, which candidates were dead, which parameters failed.
\qsa{}'s retrieval went through two designs (details in Appendix~\ref{app:apparatus}).
In \textbf{May 2025} (commits \code{2933be4}, \code{7943e46}), each session is saved on exit as one all-MiniLM-L6-v2~\cite{wang2020minilm} vector with its text, and on every turn the three stored lines closest to the latest operator message are appended to the prompt, with plot file names.
In \textbf{June 2025} (commits \code{339fbed}, \code{a233b2b}, \code{f5d7c42}), sessions are embedded in overlapping chunks of 10 turns, and retrieval becomes an action, \code{rag\_search}, that the agent invokes ``when you feel stuck, need to learn from past experience''. Each chunk carries the names of the plots it refers to, and the \code{vision} action accepts paths into earlier run folders, so the agent can reopen a historical plot.
In the committed June code, saving on exit fails because the chunking code uses a variable before assigning it, so no June session was embedded; the public release fixes this.
The corpus is the lab's own past agent sessions; no external documentation is indexed.

\subsection{Evolution of the agent}
\label{sec:evolution}

From the log formats and commit history we identify six versions (Figure~\ref{fig:timeline}, bottom; Appendix~\ref{app:apparatus}): \textbf{v0} (February--March, gated, several actions per reply), \textbf{v1}/\textbf{v1b} (April refactor), \textbf{v2} (2 May retrieval prototype, development machine), \textbf{v3} (14 May lab version, automatic retrieval, no logged gate) and \textbf{v4} (June code, run on the hardware once, on 16 June).

\section{Deployment and results}
\label{sec:results}

\subsection{Overview}

They contain 36 sessions, where a session is a part of a log with no gap longer than 3\,h.
A session counts as reaching the hardware if its script output contains instrument-driver messages or a ``saved data'' line.
A measurement counts as \emph{completed} only if such a line appears inside logged script output; a line inside an LLM reply does not count.
This definition matters.
Counting every ``saved data'' line in the logs would give 79 for February--May, because the LLM invented 7 such lines (Section~\ref{sec:failures}); the correct count is 72, or 73 including the 16 June scan.

\subsection{Case study: 14 May 2025}
\label{sec:case}

\begin{figure}[t]
  \centering
  \includegraphics[width=0.74\linewidth]{figures/fig2_case_chain_14may.pdf}
  \caption{The 14 May 2025 chain (run \code{run\_20250514\_082859}). (a) Galvo scan at 08:31, as rendered by the lab toolkit (its x-axis label is clipped in the original file). (b) \code{find\_nv} on candidate~3 at 11:23, re-centred by the operator (the overlapping red and green labels are in the toolkit's original). (c) z-focus optimize at 09:23 on candidate~1; candidate~3 went from \code{find\_nv} straight to ESR. (d) CW ODMR on candidate~3 (2.85--2.89\,GHz, 40 points, 0\,dBm, 50 averages, 175\,s) with a two-Lorentzian fit that we performed for this report; the toolkit fitted nothing. Data recovered from git commit \code{b316b58}.}
  \label{fig:case}
\end{figure}

The operator opened the session with ``characterize all the NV in the field of view''.
The agent read the default galvo configuration, wrote its own, and ran the scan (49\,s; Figure~\ref{fig:case}a).
It then requested a vision analysis of the scan, but in the same reply it had already written four coordinates.
The logged vision result repeats that list word for word, and none of the four matches a spot.
The operator read six candidates off the plot instead and told the agent to ``remember the locations''.
The agent kept this list across the 3.4-hour session and worked through it:
\begin{itemize}[leftmargin=*]
  \item \textbf{Candidate~1.} Two \code{find\_nv} runs (the second re-centred by the operator), two z-optimizations (maximum 9.24\,kcps; Figure~\ref{fig:case}c) and two ESR sweeps (2.82--2.92 and 2.72--2.82\,GHz at $-8$\,dBm), with no resonance.
  \item \textbf{Candidate~2.} Three \code{find\_nv} runs, one optimize and three sweeps, including one at 0\,dBm, again with no resonance.
\end{itemize}
Asked ``can you look at the historical attempts and tell me why we are not seeing ESR'', the agent summarised both candidates from the transcript.
It listed possible causes in three groups: \emph{microwave delivery} (antenna or wire position, power reaching the NV), \emph{NV properties} (misalignment with the field, a different charge state, different resonance frequencies) and \emph{equipment status} (recurring PulseBlaster errors in the logs).
The operator checked the microwave delivery physically and moved on.
On candidate~3 the operator re-centred \code{find\_nv} and, after one empty sweep, asked for a 2.85--2.89\,GHz window at 0\,dBm.
The agent wrote a configuration with exactly these values.
The sweep showed two dips (Figure~\ref{fig:case}d), and the operator logged ``good we see ESR''.
The session continued to candidate~4 (two \code{find\_nv} runs) before it ended.
In a short afternoon session the same day, the agent took a configuration key (\code{esr\_RnS}) for a script name.
The parser rejected the command, and the agent corrected it on the next turn (39\,s from the error to the corrected run; Appendix~\ref{app:logs}).

\paragraph{The candidate-3 spectrum.}
No spectrum in the deployment was fitted at the time.
For this report we fitted the candidate-3 sweep with weighted Lorentzian models (Appendix Figure~\ref{fig:esrfit}).
Two dips with a shared width are preferred over one dip ($\Delta\mathrm{AIC}=10.5$; $\chi^2/\mathrm{dof}=27.6/34$ versus $42.1/36$) and over a flat line.
The dips sit at $f_1=2863.1\pm0.8$\,MHz and $f_2=2877.5\pm0.5$\,MHz, with contrasts of $2.4\pm0.6\%$ and $3.9\pm0.6\%$.
Their mid-point (2870.3\,MHz) is consistent with $D$, and their splitting is $\Delta f=14.4\pm0.9$\,MHz (statistical; modelling choices give 14.4--15.7\,MHz).
If interpreted as a Zeeman splitting, it would correspond to $B_\parallel=\Delta f/2\gamma\approx2.6$\,G.
The bias field on 14 May is not known, however, and strain or other local effects could also split the resonance, so we do not attribute the splitting to an applied field.
This is a single 175\,s sweep with a few-percent contrast; it shows that the chain reached a resonance, not a precision measurement.

\paragraph{Division of labour.}
The agent wrote configurations, invoked scripts, kept the candidate list, summarised earlier attempts and listed hypotheses.
The operator chose the candidates, re-centred scans, chose the frequency windows, and checked the microwave delivery physically.

\subsection{Guidance and troubleshooting}
\label{sec:guidance}

\paragraph{Parametric guidance was followed exactly.}
We tested every operator message that named coordinates, a frequency range or a power against the next configuration the agent wrote.
In 22 of 22 cases the configuration contained exactly the requested values: 11 \code{find\_nv} centres, 10 ESR windows and one power change.

\paragraph{Domain knowledge was adopted within a session but not across sessions.}
On 19 April the operator tagged messages \code{\#rule}, \code{\#experience} and \code{\#suggest}, for example that an ESR count rate far below the \code{find\_nv} rate suggests a quenched NV.
The agent restated each point in its next reasoning block and acted on it; after the quenching hint it compared 11.5 with 2.9\,kcps and moved to the next candidate (Appendix~\ref{app:logs}).
None of these lessons reappears in any later log.
The 19 April session predates the embedding store, and on 14 May the operator, not the agent, made the equivalent call.

\paragraph{Script failures.}
Of 92 run commands, 73 completed and 19 failed; the agent recovered from the 14 May parse error, but not from most other failures (Appendix~\ref{app:results}).

\subsection{Failure analysis}
\label{sec:failures}

\paragraph{Invented tool output.}
Because the history was serialized as a flat \code{User:}/\code{Assistant:} transcript, the model sometimes continued the transcript on its own.
29 of the 311 February--May replies (9.3\%) contain invented \code{User:} or \code{Assistant:} lines, and 32 of 321 (10.0\%) with 16 June.
Five February--May replies (in v0 and v1b) invent script output, with seven fabricated ``saved data'' lines; three replies on 16 June add three more.
In one reply on 11 March the model invented an operator permission, an optimize run and an ``optimized position''.
The real optimize run failed, yet the agent planned the next ESR measurement at the invented position; the operator refused the write, the run and the plot analysis.
The parser executed every \code{<action>} block in a reply, including blocks inside the invented continuation.
The permission gate therefore did real work: 19 of the 22 ``no'' answers in the logs were given to replies that contained invented turns.
Counting such lines naively would inflate the February--May measurement count from 72 to 79.
In the 14 May version, which had no gate, the three affected replies only append an invented ``\code{User: yes}'' and contain no invented results.
The June code executes only the first action of each reply, so invented actions no longer run, but it keeps the flat transcript; the 16 June test below shows that this is not enough without a human in the loop.

\paragraph{Vision was unreliable for coordinates.}
The agent made 48 vision calls, 47 of them in February--May.
Whenever candidate coordinates were needed, the operator either rejected the agent's reading (28 February: ``you did it wrong, read the plot again'') or supplied the coordinates (19 April: ``Please use the list that I read visually''; 14 May: six typed coordinates).
On 14 May the agent used vision twice in 60 calls.

\paragraph{Low ODMR contrast and no positive control.}
The clearest resonance in the record is the 14 May candidate-3 spectrum, at a few-percent contrast.
On the same day, five sweeps on candidates 1 and 2 showed none.
The agent could hypothesize causes but had no instrument-level test to distinguish them; the decisive checks (MW delivery, quenching) came from the operator.

\paragraph{Retrieval did not visibly matter.}
In February--May the only logged retrievals are five queries on 2 May on a development machine.
They returned single-line snippets (similarity 0.38--0.44) from a test conversation, and the agent replied that it saw no relevant earlier settings.
On 14 May every turn logged ``Building prompt with RAG context'', but no retrieval result appears in the logs, and no reply refers to an earlier session.
The one retrieval on the hardware, on 16 June, returned nothing relevant (Section~\ref{sec:june}).
Cross-session improvements that did happen (\code{python}$\to$\code{py}, the \code{--output-dir} fix on 14 May) were made by humans in code.

\subsection{Post-deployment auto-mode test, 16 June 2025}
\label{sec:june}

One session ran the June code (v4) on the hardware, in auto mode (\code{run\_20250616\_112227}; 11:22--11:26; 10 LLM calls after the single prompt ``characterize NV for me'').
The agent read the default galvo configuration, wrote its own and ran the scan.
The script loaded the PulseBlaster driver, which reported a communication error, and saved a scan after 63\,s; the agent sent the plot to vision.
This is the session's one completed measurement.
In the next three replies the model continued the transcript with invented \code{Assistant:} turns containing fabricated script output: a \code{find\_nv} run, an optimization (``Optimized coordinates: X=-3.92, Y=1.05, Z=0.15'') and an ESR sweep ending in ``ESR transitions found at: 2.8671 GHz, 2.8732 GHz'', followed by an invented summary that an NV had been ``successfully characterized''.
Because v4 executes only the first action of a reply, none of these invented actions ran: \code{find\_nv} was never run, and the optimize and ESR configurations the model had ``written'' are not in the run folder.
The real optimize and ESR commands that followed pointed to these missing files and failed with exit status~1.
The agent then called \code{rag\_search} for ``successful ESR measurement configurations''; its query already contained the invented ESR result, and neither returned chunk (similarity 0.57 and 0.54) concerned ESR.
The last reply reasoned ``We had some success with the earlier steps (galvo\_scan, find\_nv, optimize)'' and drafted a message that reported the invented optimized coordinates as a result and asked the operator for ESR settings; the log ends there.
Unsupervised, the agent believed its own invented results.
In the gated February--April versions the operator refused actions from such replies; here nobody was in the loop, and only the log revealed the problem.

\section{Discussion}
\label{sec:discussion}

\paragraph{What worked.}
Without hardware-specific training, a general-purpose LLM operated the measurement chain of a real confocal NV setup through a narrow, text-only interface: JSON configurations, four scripts, and plots.
It translated every parametric operator instruction into the requested configuration (22 of 22), kept track of a six-candidate list over 3.4 hours, recovered from a script-name error within one turn, and produced reasonable hypotheses when a measurement failed.
Because the agent could act only through parameter values passed to the lab's own toolkit scripts, its mistakes stayed within what an ordinary user of those scripts could do.
The detailed logs made every measurement auditable after the fact, which is what allowed us to find the fabricated output after the fact.

\paragraph{What did not.}
The physics outcome was modest: few-percent ODMR contrast on one candidate in the best session, with no fit at the time.
The agent depended on the operator's domain priors for every scientifically important decision: which spots were NVs, where to centre, which frequency window to try, when an NV was quenched, and whether the microwaves reached the sample.
Reading coordinates from plots, which the workflow needs, failed.
\qsa{} ran only CW ODMR, so it never reached the pulsed measurements, where automation would help most.
Learning across sessions remained a design rather than an observed effect.
Left unsupervised in June, the agent reported invented results as its own progress.

\paragraph{Lessons for agents in quantum labs.}
\begin{enumerate}[leftmargin=*]
  \item \emph{Use structured chat messages, not a flat transcript.} A flat \code{User:}/\code{Assistant:} prompt invites the model to write the operator's next turn and the instrument's output, and an action parser that executes every block turns that into real actions.
  \item \emph{Gate actions, and log the gate.} The gate gave the operator a point at which to refuse actions from replies with invented turns, and 19 of 22 refusals did so; when the gate disappeared on 14 May, so did the record of what was approved, and in the ungated auto mode of 16 June invented results went unchallenged.
  \item \emph{Executing one action per turn is not enough.} It stopped invented actions from running, but not invented results from entering the transcript, the retrieval query and the agent's own summary. Tool output should be marked by the harness, for example in separate tool-result messages, so that the model cannot forge it.
  \item \emph{Count only what the instrument wrote.} Any summary statistic must be computed from tool output, not from text the model produced.
  \item \emph{Give the agent numerical tools for numerical reading.} Peak finding, fitting and spot detection should be tools; asking a vision model for coordinates was not reliable.
  \item \emph{Make lessons persistent and explicit.} The operator's tagged rules (\code{\#rule}, \code{\#experience}) were exactly the kind of knowledge that should persist across sessions. We expect that a small store of explicit lab rules would serve better than retrieval over raw conversations.
\end{enumerate}

\paragraph{How the field has moved.}
Since early 2025 LLM agents have formalized per-action authorization~\cite{wang2026artiq}, kept persistent lab memories~\cite{sha2025qcopilot,vriza2025learnonjob}, moved toward rule engines in which the LLM handles only language and exceptions~\cite{fan2026qmclaw}, and, on NV centers, run pulsed protocols autonomously for many hours~\cite{isogawa2026nv}.
\qsa{} is an early, mostly human-supervised point on this trajectory, and we offer its record mainly as a dated, honest account of what such an agent could and could not do in early 2025.

\section{Limitations}
\label{sec:limitations}

\begin{itemize}[leftmargin=*]
  \item \textbf{Scale.} This is a deployment record, not a controlled study. It covers 16 hardware sessions on one setup, with one main operator pair, and has no baseline (for example, the same tasks run by hand).
  \item \textbf{Provenance.} The exact code of several versions is not in git: the February--March code predates the first commit, 19 April used an uncommitted variant, and the 14 May code differs from the nearest commit. The models used per session rest on the authors' record; the logs do not name them.
  \item \textbf{Missing logs.} Some sessions (12 May; 14 May 07:56) are known only from embedding snapshots.
  \item \textbf{Physics.} Only CW ODMR was run, and the one fitted spectrum is a single low-contrast sweep whose splitting cannot be attributed to a known field.
  \item \textbf{Barely tested features.} The June features ran on the hardware only in the four-minute auto-mode test of 16 June 2025; no logged hardware session used assistant mode or reopened a historical plot.
  \item \textbf{Priority.} Our priority statement compares an internal log date with other groups' public posting dates, and our literature search relied on arXiv and Crossref because Semantic Scholar was unavailable; work not on arXiv may be missed.
\end{itemize}

\section{Supplementary system details}
\label{app:apparatus}

\paragraph{Hardware and scripts.} An NI~6353 DAQ steers the galvo mirrors and the z-piezo with analog outputs and counts photons; a Rohde~\&~Schwarz generator, addressed over VISA, provides the microwaves; a SpinCore PulseBlaster is loaded by every script. Positions are given as control voltages; the repository contains no voltage-to-micron calibration. \code{galvo\_scan} rasters the field of view (default $126\times126$ points over $\pm4$\,V, 2\,ms per point); bright spots are NV candidates. \code{find\_nv} takes a $61\times61$ zoomed scan over a 0.35\,V square around a chosen point, fits a 2D Gaussian and moves the beam to the fitted maximum. \code{optimize} maximizes the count rate with 1D sweeps (default: z only, 41 points over 0.6\,V). \code{ESR} sweeps the microwave frequency from \code{freq\_start} to \code{freq\_stop} at power \code{power\_out}, averaging \code{esr\_avg} times and normalizing to a reference (default 2.90--2.95\,GHz, 100 points, $-8$\,dBm).

\paragraph{Prompting.} The system instruction states the overall goal (``systematically measure the ESR of multiple NV centers in a diamond chip''), describes each script's inputs, outputs and caveats, gives the typical workflow, lists the default configuration paths, and fixes the run-command format. It tells the agent to read the default configuration first and then change parameter values only. Until June the history was serialized into a single flat \code{User:}/\code{Assistant:} transcript; Section~\ref{sec:failures} shows why this mattered.

\paragraph{Vision.} The agent reads every plot type through the \code{vision} action, which sends the PNG together with recent context to the vision model. For galvo scans the prompt asks it to read out the centre coordinates of bright spots.

\paragraph{Retrieval details.}
\begin{itemize}[leftmargin=*]
  \item \textbf{May 2025 (commits \code{2933be4}, \code{7943e46}).} On exit, the whole session is saved as one 384-dimensional all-MiniLM-L6-v2 vector together with its text. On every turn the latest operator message is used as a query. Stored sessions are split into lines and re-embedded, and the top three lines (FAISS, L2 distance) are appended as ``relevant context from previous conversations'', together with plot file names.
  \item \textbf{June 2025 (commits \code{339fbed}, \code{a233b2b}, \code{f5d7c42}).} Chunks of 10 turns with an overlap of 5. \code{rag\_search} uses a contextualized query and returns the top two chunks by cosine similarity in a delimited ``past experiments'' block. The save-on-exit bug dates from \code{34b0137} (14 June 2025).
  \item \textbf{Unmerged.} A separate branch (\code{dd6fe22}, 31 May) added distinct error and general memories that are written automatically when a script fails.
\end{itemize}

\paragraph{Agent versions.} \textbf{v0} (18 Feb -- 14 Mar) predates the repository; its first commit (3 April 2025) imports these logs. It allows several actions per reply, all gated. \textbf{v1} (April) refactors the code into per-project folders, and \textbf{v1b} (19 April) is an uncommitted local variant of it. \textbf{v2} (2 May) is the retrieval prototype, run on a development machine, and \textbf{v3} (14 May) is the May lab version with automatic retrieval and no logged gate. The June 2025 code, \textbf{v4} (assistant and auto modes, one action per turn, \code{rag\_search}, historical plot analysis), is the most developed; it ran on the hardware once, in a four-minute auto-mode test on 16 June 2025.

\section{Supplementary results}
\label{app:results}

\paragraph{19 April tagged guidance.} On 19 April the operator tagged messages \code{\#rule}, \code{\#experience} and \code{\#suggest}. For example: \begin{itemize}[leftmargin=*]   \item \code{\#experience}: single-NV contrast is ``a few percent (bad) to 20\% (best)'', followed by a suggestion to scan 2.80--2.84\,GHz.   \item \code{\#suggest}: when the count rate during ESR is far below the \code{find\_nv} count rate, the NV may be quenched and one should move on. \end{itemize} The agent restated each point in its next reasoning block and acted on it. After the \code{\#experience} message it wrote a 2.80--2.84\,GHz configuration. After the \code{\#suggest} message it compared 11.5 with 2.9\,kcps, abandoned that NV, and moved to the next candidate (Appendix~\ref{app:logs}). None of these lessons reappears in any later log. The 19 April session predates the embedding store, and on 14 May the operator, not the agent, made the equivalent call.

\paragraph{Script failures.}
Of 92 run commands, 73 completed and 19 failed.
The agent recovered from the 14 May parse error.
It did not recover from the five ``\code{python}'' invocations on 19 February (the next session used \code{py}, a change made in code between sessions), nor from the exit-127 failures on 8 April, which are consistent with running the Windows launcher on a development machine.
The two failures on 16 June are discussed in Section~\ref{sec:june}.

\paragraph{Messages ahead of results.}
Before the June one-action rule, a single reply could contain both a \code{run} and a \code{message}.
On 14 May the message announcing ``I've started the ESR measurement'' was composed before the run's result and so reported success for a command that had failed.

\section{Extended related work}
\label{app:related}

\paragraph{Other laboratory agents.} Self-driving laboratories are reviewed in~\cite{tom2024sdl}. Since 2025, agents have run an X-ray nanoprobe beamline with human-in-the-loop corrections stored in a vector database~\cite{vriza2025learnonjob}, multistage experiments at an accelerator facility~\cite{hellert2025accelerator}, and multi-day cryogenic transport measurements~\cite{bauer2026transport}.

\paragraph{Other quantum platforms.} After k-agents~\cite{cao2024kagents}, LLM agents have addressed superconducting qubits~\cite{li2026scqubit,xu2026vibe,fan2026qmclaw}, trapped ions with per-action authorization tokens~\cite{wang2026artiq}, neutral atoms~\cite{dalyac2026neutralatom} and optics~\cite{uddin2025optics,lopez2026opticsvlm}, and a benchmark tests vision-language models on reading calibration plots~\cite{cao2026qcaleval}. Classical ML has also automated quantum devices without language models, for example tuning of a semiconductor spin qubit~\cite{schuff2024spinqubit}.

\paragraph{Classical automation of NV experiments.} Adaptive Bayesian methods choose measurement settings on the fly for single-NV magnetometry~\cite{bonato2015adaptive,santagati2018magnetic}, CW ODMR~\cite{dushenko2020odmr} and Ramsey measurements~\cite{mcmichael2021ramsey}, with simplified adaptive-design algorithms in~\cite{mcmichael2022optbayes}; FiND~\cite{sahoo2023find} focuses on point emitters without imaging; neural networks speed up Ramsey characterization~\cite{shang2026nvramsey}. These methods optimize inside a fixed protocol; a Bayesian ODMR routine could serve as one of \qsa{}'s tools.
